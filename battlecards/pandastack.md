## Summary

PandaStack (pandastack.ai) is a hosting platform for AI-agent workloads built on Firecracker microVMs — the same hypervisor-based virtualization AWS Lambda and Fargate use — rather than containers. Its product surface (per its own GitHub README) spans disposable compute sandboxes, managed Postgres 16 databases, and **git-driven app hosting**, with MCP server hosting marketed as one use case of the "apps" product.

**Key structural fact (the question this battlecard was asked to resolve): PandaStack hosts MCP server code the customer already wrote — it does not convert an existing REST API or database into an MCP server automatically.** Its own "How to Deploy a Remote MCP Server" documentation describes the workflow as: you write an MCP server (stdio or Streamable-HTTP transport, in your language of choice), push it to a Git repo, and run `pandastack apps create --git-url ...` (with install/build/start commands) to have PandaStack detect the build, start the process, inject `PORT`/`HOST`, and expose a stable HTTPS URL. This is the same model as Smithery/Manufact (host code you wrote) and general PaaS providers (Vercel/Railway) — not Shredly's model (turn an API/DB into MCP with no server code to write). This is confirmed via multiple independent search-indexed quotes of PandaStack's own deployment docs, not a single unconfirmed snippet.

PandaStack's differentiated pitch versus other MCP hosts is isolation and workload fit, not no-code conversion: each app/sandbox gets its own Firecracker microVM with its own guest kernel, positioned as well-suited for MCP servers whose tools execute real, potentially dangerous operations (shell commands, filesystem writes, spawning a browser, running third-party/untrusted MCP server code) rather than MCP servers that are thin proxies in front of an API. It contrasts this with stateless-function platforms (Cloudflare Workers, Vercel) that it says fit "stateless tools that call APIs" better, positioning itself alongside Fly.io/Render/Railway for "stateful sessions in process memory."

## Features

- **Firecracker microVMs, not containers**, for every sandbox/app: hardware virtualization (KVM), own guest kernel per instance — the same VMM class AWS Lambda/Fargate use for tenant isolation. *(pandastack.ai blog, via search snippet)*
- **Boot performance:** the snapshot-restore step alone lands around 49ms; full end-to-end microVM create (network namespace allocation, rootfs reflink, VMM fork, snapshot load/resume, readiness probe) is p50 179ms / p99 ~203ms. No warm pool — every create restores a pre-baked template snapshot on demand; the one-time cold boot that produces a template snapshot is ~3 seconds. *(pandastack.ai blog, "Anatomy of a Sub-200ms MicroVM Create," via search snippet)*
- **Git-driven app hosting, no Dockerfile required:** PandaStack detects the build from the repo, starts the server process, injects `PORT`/`HOST`, and provisions a stable HTTPS hostname — called out specifically as needed for MCP OAuth metadata endpoints, which require a fixed origin. CLI flow: `pandastack apps create --git-url <repo> --install-command ... --build-command ... --start-command ...` then `pandastack apps deploy`. *(pandastack.ai blog, "How to Deploy a Remote MCP Server," via search snippet)*
- **Scale-to-zero via snapshot restore:** idle apps/servers can sleep and resume from a memory snapshot rather than a cold container/process start, framed as avoiding the cold-start penalty typical of scale-to-zero container platforms. *(pandastack.ai blog, via search snippet)*
- **No MCP-transport rewrite required per PandaStack's own docs:** tool/resource/prompt implementations are described as transport-agnostic — a stdio MCP server's logic doesn't need to change, only the entrypoint/transport wiring (adding a Streamable-HTTP listener) to run remotely. PandaStack's docs flag that tools assuming local filesystem/localhost access (valid for a stdio server) will break once moved to a remote host and need review. *(pandastack.ai blog, via search snippet)*
- **MCP/tool-execution isolation as the differentiated use case**, called out repeatedly across multiple PandaStack blog posts: running untrusted or third-party MCP servers, or tools that shell out, write files, spawn a browser, or run model-authored code, inside a disposable per-instance microVM rather than a shared container kernel; recommends denying outbound network by default and proxying tool calls across the VM boundary for untrusted servers. *(pandastack.ai blog posts: "Isolate Untrusted MCP Servers in MicroVMs," "Secure MCP Tool Execution in MicroVMs," "Sandboxing LLM Tool Calls & MCP Servers," via search snippets)*
- **Managed PostgreSQL 16** (marked Beta), each database in its own durable microVM. *(GitHub README, direct fetch; corroborated by search snippets)*
- **Positioning vs. other MCP hosts** (per PandaStack's own "Best MCP Server Hosting Platforms in 2026" post, via search snippet): stateless proxy-style tools are better served by Cloudflare Workers or Vercel (lower latency, less operational surface); stateful, long-running, or heavier-tool-execution servers are better served by long-running-process platforms — Fly.io, Render, Railway, and PandaStack are grouped together in that category.
- **Open-source core is self-hostable** (Apache-2.0, `pandastack-io/pandastack-ai` on GitHub) — sandboxes + Postgres with full lifecycle control (pause/resume/hibernate/wake/TTL/idle-reaping, snapshot fork, persistent volumes, network isolation) — but explicitly excludes the git-driven app hosting used for the MCP-deployment workflow described above; that layer is cloud-only. *(GitHub README, direct fetch)*

## Where Shredly wins

- **No server code to write, ever.** PandaStack hosts an MCP server *you already wrote* (stdio or HTTP transport, pushed via Git) — you're still on the hook for implementing MCP tool/resource/prompt handlers, choosing a transport, and fixing assumptions that break when moving from local/stdio to remote (per PandaStack's own docs). Shredly turns an existing REST API, database, or internal tool into a hosted MCP server without the customer writing that server code at all (per CLAUDE.md) — a materially different starting point for the "I have an API, no MCP server yet" buyer that is Shredly's core ICP.
- **Simpler, predictable flat pricing for a budget-conscious SMB buyer.** Shredly: Free / $10/month shared / $50/month private — three fixed numbers, no rate card to model (per CLAUDE.md). PandaStack's confirmed pricing signal is usage-based ($0.054/active-vCPU-hour + $0.0162/GiB-hour working-set memory beyond a small free credit) — better for elastic/bursty compute workloads, but it means an SMB team has to estimate compute-hours and memory footprint to predict its bill, rather than picking a tier.
- **Purpose-built MCP protocol handling out of the box.** Per CLAUDE.md, Shredly is purpose-built for the MCP protocol (auth, tool/resource schemas, client compatibility with Claude Desktop/Cursor/Continue/Windsurf) without the customer wiring any of it. PandaStack's MCP support, per its own docs, is "bring a server that speaks Streamable HTTP with a stable HTTPS host" — it solves hosting/infra and isolation, not MCP schema/tool authoring, session-state architecture (its own docs flag that multi-instance deployments need Redis/DB-backed session state if the server isn't stateless), or client-compatibility wiring.
- **No infrastructure concepts to learn.** PandaStack's workflow involves microVMs, snapshot-restore semantics, active-CPU/working-set billing units, and a CLI (`pandastack apps create/deploy`) — closer to a general infra/PaaS mental model (the CLAUDE.md "vs. general PaaS" comparison point) than Shredly's "sign in, grab a key, point a client at it" flow.

## Where they win / honest gaps

- **Stronger isolation story for MCP servers that execute real operations.** PandaStack's core differentiator — a dedicated Firecracker microVM (hardware-virtualized, own guest kernel) per app/sandbox — is a materially stronger security boundary for MCP tools that shell out, write files, spawn a browser, or run untrusted/third-party server code than typical container- or process-level isolation. If a prospect's MCP server needs to execute arbitrary or risky operations (not just proxy read calls to an API), PandaStack's isolation model is a legitimate, well-documented (across multiple of its own blog posts) advantage that should not be waved away — Shredly should be honest about what isolation model it runs on if asked in this scenario rather than asserting parity without a source.
- **Elastic/usage-based pricing can be cheaper at low, bursty utilization.** Billing on active-CPU-seconds and working-set memory (not reserved capacity) means a genuinely idle or spiky MCP server could cost less on PandaStack than a flat $10-$50/month Shredly tier — worth acknowledging rather than claiming Shredly is unconditionally cheaper.
- **Supports any language/runtime you can build and start via a Git repo**, not a fixed set of source connectors — a team with a nontrivial, already-written custom MCP server (complex tool logic beyond wrapping an API/DB schema) has more flexibility hosting that code as-is on PandaStack than fitting it into a schema-driven, no-code conversion model.
- **Broader platform, not single-purpose.** PandaStack's sandbox/microVM infrastructure also targets AI code-execution, agent computer-use, browser automation, and untrusted-code-sandboxing use cases beyond MCP — a team already using it for those workloads has an argument for consolidating MCP hosting onto the same platform rather than adding Shredly as a separate vendor. Not evaluated here whether that consolidation logic holds for a pure "expose our API to agents" buyer, since that's a different job to be done.
- **Open-source, self-hostable core** (Apache-2.0) is a credible answer for a team that wants to avoid vendor lock-in entirely and is willing to run its own infrastructure — a segment of the self-hosting alternative Shredly already competes against per CLAUDE.md, but one where PandaStack offers a maintained OSS project as a starting point rather than the DIY-from-scratch baseline.

## Facts

- PandaStack (pandastack.ai) hosts MCP server code the customer already wrote (Git repo, stdio or Streamable-HTTP transport) — it does not automatically convert an existing REST API or database into an MCP server. (Confirmed via multiple search-indexed quotes of PandaStack's own deployment docs, checked 2026-09-16; not independently verified via direct page fetch, which was blocked in this session.)
- Shredly (per CLAUDE.md) converts an existing REST API, database, or internal tool into a hosted MCP server without the customer writing server code.
- PandaStack's compute/isolation model is Firecracker microVMs (hardware virtualization, one guest kernel per app/sandbox), not containers.
- PandaStack app deployment: Git-driven, no Dockerfile required; auto-detects build, injects `PORT`/`HOST`, provisions a stable HTTPS hostname (called out for MCP OAuth-metadata needs). CLI: `pandastack apps create --git-url <repo> ...` / `pandastack apps deploy`.
- PandaStack microVM performance figures per its own blog (via search snippet, checked 2026-09-16): ~49ms for the snapshot-restore step alone; p50 179ms / p99 ~203ms end-to-end microVM create; ~3 seconds for a one-time cold boot that produces a reusable template snapshot.
- PandaStack scale-to-zero uses snapshot restore (resume from memory snapshot) rather than a container cold start.
- PandaStack pricing (not confirmed via direct fetch, checked 2026-09-16): free tier with no credit card required and a stated $5.40/month usage credit; usage-based rate card of $0.054 per active-vCPU-hour and $0.0162 per GiB-hour of working-set memory beyond the free credit; no named flat higher-tier plan (e.g. "$X/month Pro") was found for pandastack.ai in this session.
- Shredly pricing (per CLAUDE.md, confirm at shredly.io/pricing before quoting): Free (Google sign-in, shared environment, base limits); Shared $10/month (shared environment, expanded limits); Private $50/month (private/isolated MCP server, more granular controls).
- PandaStack's open-source core (`pandastack-io/pandastack-ai`, GitHub, Apache-2.0) provides microVM sandboxes and managed Postgres 16, self-hostable and unmetered; it explicitly excludes git-driven app hosting, serverless functions, cron, PR previews, and custom domains — those are PandaStack Cloud-only features.
- PandaStack positions itself for MCP servers whose tools execute real operations (shell commands, filesystem writes, browser automation, untrusted/third-party MCP server code) rather than MCP servers that are thin proxies over an API; its own comparison content recommends Cloudflare Workers/Vercel instead for stateless, API-proxy-style MCP servers.
- A `pandastack.io` site ("Your Personalised DevOps," Starter/Pro/Team/Enterprise tiers) also appeared in search results; the GitHub org for pandastack.ai's open-source project is named `pandastack-io` (company: Pandastackio Inc), suggesting a relationship between the two domains, but this was not independently confirmed by direct fetch of either site in this session — pandastack.io figures are excluded from this battlecard.
